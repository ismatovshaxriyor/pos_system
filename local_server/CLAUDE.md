# local_server — guidance for Claude Code

This file loads automatically when working with files under `local_server/`. See `DEPLOY.md` for full deployment & mDNS auto-discovery setup, repo-root `CLAUDE.md` for the two-project overview, and `local_server/core/CLAUDE.md` for the `core` app's architecture.


### Dev commands (port 8000, Postgres 127.0.0.1:15432, Redis 127.0.0.1:16379)
```bash
cd local_server
docker compose up -d --build       # web, db, redis, celery_worker, celery_beat, db_backup
docker compose exec web python manage.py makemigrations core licensing   # only after changing models - commit the generated files (see repo-root CLAUDE.md)
docker compose exec web python manage.py migrate
docker compose exec web python manage.py createsuperuser
docker compose exec web python manage.py test licensing        # or: core / licensing.tests.test_middleware etc.
docker compose exec web python manage.py activate_license <KEY>  # CLI onboarding, calls ActivateView in-process
docker compose exec web python manage.py seed_demo_data [--days N]  # fills the dev DB with a realistic restaurant (tables, staff, days of orders) for manual/demo testing
docker compose logs -f celery_beat   # watch send-heartbeat / renew-license-daily firing every ~60s / daily 03:00
make cleardata   # django flush (interactive confirm) - wipes data, keeps schema
make user        # createsuperuser shortcut
```
Admin UI: `http://localhost:8000/admin/` · Swagger: `http://localhost:8000/api/docs/` · Auth: `POST /api/auth/login/` (DRF token)

First-time licensing setup (generating/placing the RSA keypair) is a one-time onboarding task — see the `setup-licensing` skill rather than repeating it here every session.

### Bringing up a fresh prod-compose instance (new restaurant, or a local "what would a new restaurant see" test)
**One command: `scripts/install.sh` (Linux/macOS) / `scripts/install.ps1` (Windows)** — asks the user exactly **one** thing: whether to allow **online mode** (and, only if yes, the Cloudflare tunnel token). Everything else is generated/derived automatically: `SECRET_KEY`/`DB_PASSWORD`/`WATCHTOWER_TOKEN`, the hardware fingerprint, `POS_IMAGE` (from the git remote), image source (tries `docker pull`, silently falls back to a local `build` if the pull fails), Ona URL (default), and the license public key (Ona sends it at activation → stored in `LicenseState.public_key`; `keys/license_public.pem` is only an optional fallback, never prompted). Overrides are `POS_*` env vars only (`POS_ONLINE`, `POS_CF_TOKEN`, `POS_LICENSE_KEY`, `POS_MODE`, `POS_IMAGE`, `POS_GHCR_USER/TOKEN`, `POS_ONA_URL`, `POS_PUBLIC_DOMAIN`, `POS_MDNS=0`, `POS_NO_SLEEP=0`). It replaced the earlier `setup-new-restaurant.sh`.
- **Online vs offline mode (`ONLINE_MODE` in `.env`)**: restaurant WiFi often has no internet. Offline mode brings up only `db db_backup redis web celery_worker celery_beat website` — `cloudflared` (remote access) and `watchtower` (auto-update) are never started (and removed if a previous online install created them). The POS itself (orders, payments, printing, staff apps over LAN, mDNS) is unaffected; the Celery Ona tasks (heartbeat/renew/error-log/order-sync/app-release mirroring) already tolerate `requests.RequestException`, so no code short-circuit exists. **First install and first license activation need internet once** (image pull / `website` build / Ona activation); after that the Bola survives weeks offline on `LicenseState.pending_tokens`, and an exhausted batch is recovered with an offline token entered on the staff apps' blocked screen (`POST /api/license/apply-offline-token/`, `pos.applyOfflineToken`). The installer refuses to proceed without internet unless the needed images already exist locally. Not working offline: Telegram alerts, remote commands/updates, Ona sync, Google Fonts in `qr_app.html`/`kitchen_dashboard.html`.
- **Resource profile (automatic, no question asked)**: the installer reads RAM/cores (and warns on HDD / <15 GB free / <3 GB RAM) and writes `RESOURCE_PROFILE=small|mid|large` plus the knobs `docker-compose.prod.yml` consumes into `.env` — `CELERY_MAX_CONCURRENCY` (worker runs `--autoscale=MAX,1`, so it idles at 1 process and only grows under load; `--max-memory-per-child` recycles leaky children), `PG_SHARED_BUFFERS`/`PG_MAX_CONNECTIONS`/`PG_WORK_MEM`/`PG_EFFECTIVE_CACHE_SIZE` (Postgres `-c` flags, restart-time only), `REDIS_MAXMEMORY` (policy `volatile-lru` on purpose: Celery queues and Channels layer keys have no TTL and must never be evicted; only TTL'd cache/throttle/WS-ticket keys are), `BACKUP_KEEP_DAYS/WEEKS/MONTHS`. macOS/Windows subtract ~2.5 GB (OS + Docker VM) from RAM before choosing; ≤2 cores caps at `mid`. Recomputed on every run (secrets untouched); override with `POS_PROFILE`. Compose defaults equal `mid`. **Deliberately not done:** hard `mem_limit` (OOM-kill on a till is worse than slowness) and a runtime controller that resizes containers (would need `docker.sock`, see security posture). All prod services share a `json-file` log rotation (10 MB x 3) — unbounded Docker logs were the realistic way a small disk fills up.
- **Disk-pressure guard** (`licensing.tasks.disk_guard`, hourly beat): `DISK_WARN_PCT` (85) → drops already-reported `ErrorLog` rows older than 1 day; `DISK_CRITICAL_PCT` (92) → additionally `clean_old_history --auto --days HISTORY_PRUNE_DAYS_ON_PRESSURE` (180, audit trail older than that is sacrificed) and, if still critical, one `logger.error` per 6 h that rides the normal ErrorLog → Ona channel (visible in the Ona admin). Backups/Docker logs are not visible from the app containers — they're bounded by `BACKUP_KEEP_*` and log rotation.
- **Linux** (apt/dnf/yum via `get.docker.com`; pacman/zypper packages): installs Docker + compose plugin, enables the service, adds the user to the `docker` group (and uses `sg docker` for the rest of the run so no re-login is needed), opens ufw/firewalld ports 8000/tcp + 5353/udp, masks sleep targets and ignores the lid switch via a `logind.conf.d` drop-in, installs avahi through the existing `setup_avahi.sh`, optionally the printer-subnet aliases.
- **macOS**: Docker Desktop via `brew --cask` (it refuses to auto-install Homebrew itself), `pmset sleep 0 autorestart 1`, a launchd agent running `dns-sd -R` for mDNS.
- **Windows**: self-elevates (UAC), enables the WSL/VirtualMachinePlatform features (stops and asks for a reboot if needed — answers are already in `.env`, so just re-run), installs Docker Desktop via winget, waits for the engine (first launch needs the user to accept Docker's terms in its window), a "POS Bola Docker" scheduled task (runs as the console user at logon and every 5 min, restarts Docker Desktop if its process is gone; at Rohat Docker Desktop failed to come up after a reboot despite its HKCU Run entry and the POS was down for ~40 min; when Docker Desktop is running but the engine has not answered for 5+ min it kills Docker Desktop, runs `wsl --shutdown` and starts it again, with a 30-min cooldown — this is the dialog's "Restart" button; at Rohat on 2026-11-22 a Microsoft Store WSL auto-update at 04:06 left Docker Desktop stuck on "WSL is unresponsive" and the POS was down 4.5 h, because the process was alive and the old check ignored it; it also `docker restart`s the `web` container when port 8000 refuses connections twice 30 s apart while containers are up — when the engine came back that morning (plus a LAN cable re-plug), `com.docker.backend`'s port forwarder was stale, so 8000 answered nobody, not even localhost, while heartbeats kept succeeding; any HTTP response counts as alive, 15-min cooldown, containers younger than 3 min are skipped), firewall rules, the `_pos-bola._tcp` mDNS advertiser task (`scripts/advertise_mdns_windows.ps1 -Install`, see repo-root CLAUDE.md), `powercfg` no-sleep/no-hibernate/lid-ignore.
- **Common**: scaffolds `.env` (random `SECRET_KEY`/`DB_PASSWORD`/`WATCHTOWER_TOKEN`; `POS_IMAGE` derived from the git remote; `LICENSE_ENFORCEMENT=1`), pulls (or with `--build`/`-Build` builds) the image, brings up `docker-compose.prod.yml` (explicit service list — `cloudflared` only with a real token in online mode, `watchtower` only in online mode), waits for `/api/discovery/`, runs `activate_license` (skipped if already activated — Ona auto-provisions the first manager on activation, so no account prompt), then re-probes via the LAN IP and prints the `ALLOWED_HOSTS`/stale-image diagnosis on a 400. Re-runs are safe: existing `.env` secrets and `HARDWARE_ID_OVERRIDE` are never regenerated (the license is bound to that fingerprint). `--yes`/`-Yes` = unattended (online mode defaults to off unless `POS_ONLINE`/`POS_CF_TOKEN` is set); `--config-only`/`-ConfigOnly` prepares files without touching Docker or the system.
- **Why it writes `HARDWARE_ID_OVERRIDE`**: containers on Docker Desktop (macOS/Windows) have no stable machine id, and some Linux mini-PCs report an all-zero DMI `product_uuid`; the installer derives a stable value from the *host* (macOS `IOPlatformUUID`, Windows `Win32_ComputerSystemProduct.UUID`, Linux host `/etc/machine-id` only when DMI is unusable) instead of leaving the license to bind to a fingerprint that changes.
- **Why `REGISTRY_AUTH_FILE`**: with Docker Desktop, `~/.docker/config.json` holds credentials in the OS keychain (`credsStore`), which the Watchtower container can't read, so the private ghcr image would never auto-update. The installer writes a separate `./.registry-auth.json` (gitignored, 0600, always present as a *file* — if it doesn't exist Docker creates a *directory* there and breaks the mount) and `docker-compose.prod.yml` mounts `${REGISTRY_AUTH_FILE:-~/.docker/config.json}`.
- **Image hygiene**: `local_server/.dockerignore` and `cloud_server/.dockerignore` exist because `COPY . /app/` used to bake `.env`, `backups/`, `media/` and `keys/` into locally built images (CI builds were clean only because a fresh checkout has none of them) — on the cloud, `keys/license_private.pem` (the license signing key) was inside the EC2-built image. Keys are volume-mounted at runtime, so excluding them is safe. The Cython builder no longer installs `requirements.txt` and the final stage has no apt packages/pip cache (697 → 542 MB); the list of source files deleted after compilation now comes from `licensing/setup.py::PROTECTED_MODULES` (`REMOVE_SOURCES=1`) instead of a second hand-kept list in the Dockerfile — that duplicate had drifted and `core/order_templates.py` shipped as readable source next to its `.so`.
- **Limitation**: the compose file still has `website` with `build: ../website`, so the installer must run from a full checkout (or zip) of the repo, not a source-free bundle — publishing a website image to ghcr would lift that.
- `install.ps1` has only been syntax-balanced by eye, not executed (no PowerShell on the dev Mac); `install.sh` was exercised via `--config-only` on macOS (bash 3.2), full Docker/system paths not yet run on a real restaurant machine.

**`ALLOWED_HOSTS` accepts any private LAN IP automatically** (`config/hosts.py::PrivateLANHost`, RFC1918 + `.local` — wired in via `config/settings.py`) so staff-app discovery (`http://192.168.x.x:8000`) doesn't need a per-restaurant `.env` edit. **This only exists in the image a `v*` tag actually built** (`release-local-server.yml` only builds+pushes on a tag push, never on a plain `main` push) — if you've landed a change to `config/`, `licensing/`, or `core/` on `main` without cutting a release yet, `docker-compose.prod.yml` pulling `ghcr.io/.../pos-local:stable` will still be running the *previous* release's code. This exact gap once made a freshly-built Bola reject every LAN request with `DisallowedHost` even though the fix for it was already on `main`. `.github/workflows/check-local-server-release-freshness.yml` posts a (non-blocking) warning on every `main` push touching `local_server/` when this drift exists — see its summary before assuming a pulled `:stable` image has your latest commit. To get unreleased code into a running prod-compose stack without cutting a release yet, use `install.sh --build` (or `docker compose -f docker-compose.prod.yml up -d --build`) instead of pulling.

### Rebuilding the Android staff app after a JS/TS change
`staff_apps/apps/mobile/scripts/rebuild-install.sh` wraps the local release-APK workflow (rsync to a space-free build path since ndk-build breaks on paths with spaces, `gradlew assembleRelease`, `adb install -r`, falling back to `pm install-existing --user 0` for devices — some Xiaomi/MIUI ones observed — that install successfully but not onto the active user profile, then launching the app). Pass `--full` to re-run `expo prebuild --clean` first (needed when native config, e.g. an `app.json` plugin, changed — not needed for plain JS/TS edits).

These local builds are debug-signed. Android rejects them over a CI-signed install (`INSTALL_FAILED_UPDATE_INCOMPATIBLE`) unless the `POS_ANDROID_KEYSTORE`, `POS_ANDROID_KEYSTORE_PASSWORD` and `POS_ANDROID_KEY_ALIAS` env vars are exported. Releases are built by CI, not this script; see "Building and publishing staff apps" in the repo-root `CLAUDE.md`.
